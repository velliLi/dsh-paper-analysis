# 子代理提示词模板

子代理**看不到本次会话**，因此每个 prompt 都必须自带：产物路径、材料位置、输出格式、禁编造规则。
统一头部（贴在每个 prompt 最前）：

```
你在执行论文分析流水线的一部分。
材料：<PDF 绝对路径 / paper.txt 绝对路径>（若需要请先自行提取文本，工具：pdftotext；不可用时用 read 逐段读 paper.txt）
本次分析目录：<OUT 绝对路径>
规则：(1) 绝不编造数字或引文；论文没写就写 [论文未给出]。(2) 每个结论必须带原文位置（§/p./Table/Fig）与一句原文引文。(3) 你自己的判断必须标 [推断]。(4) 只输出指定格式，不要寒暄。
写文件用 write 工具，路径 <OUT>/<文件名>；若目录不存在请创建。
```

## P2 证据提取子代理

```
<统一头部>

任务：产出「主张—证据表」，写入 20-claims.md。
步骤：
1. 通读全文，抽取所有可核查主张（性能提升、效率提升、开销更低、适用性更广、首次实现等）。
2. 对每条主张填表：ID | 主张（照抄原文关键句，英文保留原文） | 原文位置 | 证据类型（实测/post-layout/RTL/算法级/理论/引他人） | 证据强度（强/中/弱 + 一句话判据） | 我的判定。
3. 全篇只有一处支撑的主张，标注「单点证据」。
4. 最后附一节「我读不懂或看起来矛盾的地方」，逐条给页码。
输出：只写文件，返回 5 行以内摘要（主张条数、强证据条数、最值得怀疑的 1 条）。
```

## P3 实验解剖子代理

```
<统一头部>

任务：产出实验解剖，写入 30-experiments.md。
必含 6 张表（缺数据就写 [论文未给出]，不要留空）：
1 数据集/测试用例表 2 基线表（含基线来源、是否作者复现、调参力度）3 指标表（含测量条件）4 主结果表（搬运准确数字，标 Table/Fig 号）5 消融/敏感性表 6 开销表（时间/面积/功耗/内存/训练成本/扩展性）。
每张表下写 2–4 行「我的解读」，格式：作者主张 → 数据支持到什么程度 → 还缺什么对照。
输出：只写文件，返回 5 行以内摘要（主结果最强的 3 个数及其条件）。
```

## P4 创新点鉴定子代理

```
<统一头部>
补充材料：<论文自报最近邻的相关工作标题>；检索工具可用（web_search / web_fetch）。

任务：产出创新点分析，写入 40-innovation.md。
步骤：
1. 技术分解为 3–6 个构件，每个标 已知 / 已知但改造 / 新提出，并说明依据。
2. 三条基线对照：① 论文自报最近邻（逐条差异，分为 能力差异/成本差异/设计选择）；② 用 web_search 检索同期同类工作（至少 3 条查询），判断是否撞车或已被超越，给出链接与年份；③ 定位经典技术母题（参考领域常识），判断是否为母题的参数化。
3. 每条创新点写成：标题（名词化）/ 相对对象 / 为什么算新 / 支撑证据 / A–D 分级 + 一句话理由 / 可证伪表述 / 复现所需信息。
4. 结尾给「我认为最容易被审稿人攻击的创新点」1 条并说明原因。
输出：只写文件，返回 5 行以内摘要（创新点条数与最高等级）。
```

## P5 对抗验证（用 workflow 工具一次扇出三个角色）

`workflow` 脚本骨架（返回结构化 JSON）：

```js
const roles = [
  { role: 'reproducer', focus: '可复现性缺口：缺失参数/私有资源/不可复现步骤，以及等价替代会破坏什么' },
  { role: 'historian',   focus: '技术谱系：最早雏形、同期工作、是否已被后续工作超越或证伪（请用 web 检索）' },
  { role: 'reviewer',    focus: '实验设计漏洞：基线公平性、消融充分性、方差与显著性、选择性报告、结论外推' },
]
const schema = {
  type: 'object', additionalProperties: false,
  required: ['role', 'findings'],
  properties: {
    role: { type: 'string' },
    findings: { type: 'array', items: {
      type: 'object', additionalProperties: false,
      required: ['id', 'severity', 'claim', 'evidence', 'what_would_settle_it'],
      properties: {
        id: { type: 'string' }, severity: { type: 'string', enum: ['high','medium','low'] },
        claim: { type: 'string' }, evidence: { type: 'string' }, what_would_settle_it: { type: 'string' },
      } } },
  },
}
return await parallel(roles.map(r => async () => await agent(
  `你是论文审查角色「${r.role}」。材料：<PDF 或 paper.txt 路径>。\n审查重点：${r.focus}\n` +
  `规则：不编造；每条发现必须指出原文位置或明确指出"论文缺失该信息"；severity 按"是否足以推翻结论"判定。` +
  `最多 6 条发现，只输出 JSON。`, { schema, label: r.role, phase: '对抗验证' })))
```

主 Agent 拿到结果后写入 `50-critique.md`，逐条处理：

```markdown
| ID | 角色 | 严重度 | 指控 | 我的处置（接受/反驳+证据/存疑） | 落到报告哪一节 |
| R1 | reproducer | high | <...> | 接受 → §6.2 L3 | §6 |
```

**反驳纪律**：反驳必须引原文原句；引不出就不能反驳。三个角色都没提出的领域（如工艺口径），主 Agent 自己补一条。

## 并行下发建议

- P2、P3、P4 同时下发（`subagent`，默认后台），主 Agent 同时做 P1 的骨架整理。
- P4 依赖 P2/P3 的部分结论时，把 P2/P3 已完成文件的**路径**给 P4 子代理（不要粘贴全文，让它自己读）。
- P5 必须在 P2–P4 完成后跑。
- 子代理返回的产物一律视为素材：**创新点分级与报告中"我的结论"由主 Agent 自己写**。
